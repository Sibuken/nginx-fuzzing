# NGX-IF14 — кадры DATA HTTP/2

Цель направляет кадры DATA через настоящий инкрементальный парсер заголовков nginx, `ngx_http_v2_state_data` и `ngx_http_v2_state_read_data`. Каждый вход проходит четыре схемы фрагментации в профилях preread и no-buffering; для каждого повтора создаётся новое искусственное соединение. Третий профиль запускается только для структурно корректного кадра DATA без padding в потоке 1, если полезная нагрузка превышает небольшой буфер тела; кадр обрабатывается одним целым фрагментом.

Драйвер, добавляемый только при сборке, предоставляет один активный поток (ID 1), минимальный запрос с неотрицательной длиной содержимого и буфер preread размером 8192 байта. Проверяются длина и флаги DATA, padding, поиск потока, учёт окна приёма и накопление полезной нагрузки. Во втором профиле задаётся минимальный буфер `request_body` для режима no-buffering, чтобы через обработчик DATA вызвать настоящий `ngx_http_v2_process_request_body`. Фильтры тела запроса и обработка приложения не запускаются. Третий профиль использует 16-байтовый буфер тела и поглощающий верхний фильтр-заглушку, существующий только для фаззинга: при заполнении буфера вызывается настоящий `ngx_http_v2_filter_request_body`. Четвёртый профиль передаёт не менее двух структурно корректных кадров DATA одному состоянию тела запроса; END_STREAM должен быть только у последнего, буфер тела и цепочка фильтров сохраняются между кадрами. Профиль нескольких кадров с padding требует корректного padding в каждом кадре и повторяет последовательность при четырёх схемах фрагментации сети с общим буфером и цепочкой фильтров.

Ещё два ограниченных профиля для одного кадра задают совпадающий или намеренно слишком малый Content-Length. Совпадающая длина проходит обычное потребление тела и продолжение сброса буфера при чтении тела; короткая проверяет отказ nginx при превышении, который драйвер перехватывает до недоступного в искусственном запросе пути финализации ответа. Последний профиль объявляет длину на байт больше полезной нагрузки и после END_STREAM имитирует продолжение сброса буфера; настоящий фильтр тела должен отклонить недостающие данные с `NGX_HTTP_BAD_REQUEST`. Отдельный ограниченный профиль принимает только корректный одиночный DATA с padding, проверяет, что после padding остаётся не менее 17 байт полезной нагрузки, и передаёт тело через фильтр с точным Content-Length при четырёх схемах фрагментации: целый кадр, по одному байту, по три байта и по размеру фрагмента из входа. Начальные примеры охватывают тело длиной один байт, минимальное 17-байтовое тело для фильтра, ноль и один байт padding, а также максимально допустимые 255 байт padding для тел длиной один и 17 байт. Исходный пример для фильтра содержит 20 байт тела и три байта padding. Ограничение входа 4096 байт удерживает все буферы в заданных пределах; исчерпание большого окна приёма и полноценное создание запроса из HEADERS вне области цели.

Дополнительный профиль последовательности со смешанным padding требует хотя бы одного кадра DATA с padding и одного без него, корректных длин и padding в каждом кадре, завершающего END_STREAM и более 16 байт тела без учёта padding. Общие буфер тела и цепочка фильтров сохраняются; используются четыре схемы фрагментации: целиком, по одному байту, по три байта и по размеру из входа. Начальный пример `data-mixed-padding-sequence` проверяет чередование «с padding → без padding → с padding». Есть примеры «без padding → с padding», тело 15+1+2 байта на границе общего 16-байтового буфера и последовательность «с padding → без padding → с padding» с тремя размерами полезной нагрузки. Каждая содержит 18 байт тела без padding; END_STREAM есть только у последнего кадра.

Условие для длинной последовательности требует не менее шести кадров, пяти переключений состояния padding и 48 байт тела без padding. Начальный пример чередует варианты padding шесть раз, передавая по девять байт тела за кадр (54 байта всего). Общий 16-байтовый буфер многократно заполняется и сбрасывается; END_STREAM установлен только у последнего кадра с padding. Используются те же четыре схемы сетевой фрагментации.

Ещё три примера помещают кадр DATA с padding после накопления 15, 16 или 17 байт тела. Он добавляет один байт тела, а поле длины padding и один или два байта заполнения остаются вне тела запроса. В случае с 15 байтами добавляется ещё один байт без padding, чтобы превысить порог фильтра в 16 байт. Эти случаи проверяют переходы при точном заполнении буфера, а также непосредственно до и после него, с фрагментацией входа по 1 и 3 байта.

Ещё три последовательности охватывают все девять сочетаний этих исходных размеров тела и длины padding 0, 1 и 255. Каждая начинает с 15 байт тела; затем каждый кадр DATA с padding добавляет один байт. Промежуточные пустые DATA удерживают накопленное тело на отметках 16 и 17 байт. В трёх примерах длины padding чередуются на этих границах; последний блок из 255 байт padding исключается из тела запроса.
